# CLAUDE.md

Guidance for Claude Code working in this repository. Humans should read [README.md](./README.md) and [CONTRIBUTING.md](./CONTRIBUTING.md) first.

## Entry points

- `apify` CLI — `src/entrypoints/apify.ts`
- `actor` CLI — `src/entrypoints/actor.ts`

## Before you push

Run `pnpm run lint && pnpm run format && pnpm run build && pnpm run test:local` before pushing. Run `pnpm run test:api` too if you changed anything that touches the Apify API.

If you modified a command's flags, args, description, or added/removed a command, also run `pnpm run update-docs` and commit the regenerated `docs/` output.

## Code conventions

- Package manager: **pnpm 10** (via Corepack). Do not use npm or yarn.
- Use `.js` import specifiers for local files (e.g. `import { foo } from './foo.js'`). The `.ts` source resolves at build time.
- Commands extend `ApifyCommand` from `src/lib/command-framework/apify-command.ts`. Follow the pattern of existing commands: `static override name`, `static override description`, `static override flags/args`, and an `async run()` method.
- New commands must be registered in `src/commands/_register.ts` (or the parent `_index.ts` for subcommands).
- Do not add docstrings, comments, or type annotations to code you did not change. Keep diffs tight.
- Use contractions in command, flag, and arg descriptions, and in docs text: "doesn't", "can't", "aren't", not "does not", "cannot", "are not". `docs/` is generated from these strings, so fix the source.

## Install size

The CLI is installed globally by many users and in Actors, so keep the npm install footprint lean. Always look for opportunities to shrink it:

- Prefer Node.js built-ins over dependencies, and prefer dependencies already in the tree over new ones.
- Before adding a dependency, check what it drags in: `npm install <pkg>` in an empty temp dir, then `du -sh node_modules`. Mention the install-size impact in the PR description.
- When touching code that uses a dependency, check whether the dependency is still pulling its weight — a single small helper from a large package is a candidate for replacement or removal.
- To measure the CLI's own footprint, run `node scripts/report-install-size.mjs` — it packs the current tree and compares tarball, unpacked, and full-install sizes against the latest published version. The release workflows run it and embed the report in the GitHub release notes.

## Testing

- Tests use **Vitest**. See [CONTRIBUTING.md](./CONTRIBUTING.md#writing-tests) for `useAuthSetup` and `useTempPath` hook usage.
- API tests must include `[api]` in the test name and live in `test/api/`.
- Always `import process from 'node:process'` in command/lib code — never use `globalThis.process`. This is required for test cwd mocks to work.

## Pull requests

Keep PR descriptions concise: what changed and why, key numbers, follow-ups. Short bullet points over narration; don't restate the diff or describe the process.

## Things to avoid

- Do not use `--no-verify` to skip git hooks. Fix the underlying issue.
- Do not edit `docs/` by hand — it is generated by `pnpm run update-docs`.

# Task-Based Development Workflow

Before starting any new development task, create a dedicated folder under `tasks/<TASK-ID>-<task-name>/`.

Follow these steps:

1. **Create Task Folder:** Create a separate folder for the task and maintain all related Markdown documentation inside it.

2. **Analyze Existing Implementation:** Review the relevant codebase before modifying anything. Document the current execution flow, classes, methods, database dependencies, business logic, and limitations in `existing-implementation.md`.

3. **Document Requirements:** Record the business requirements, expected behavior, constraints, and acceptance criteria in `requirements.md`.

4. **Prepare Implementation Plan:** Document the proposed solution, required code changes, affected methods, and implementation sequence in `implementation-plan.md`.

5. **Perform Impact Analysis:** Identify affected modules, APIs, database operations, integrations, backward compatibility risks, and regression areas in `impact-analysis.md`.

6. **Define Test Cases:** Document positive, negative, boundary, and regression scenarios in `test-cases.md`.

> **STRICT GATE — NO CODE BEFORE APPROVAL:**
> After completing steps 1–6, present the implementation plan to the user and **wait for explicit approval**.
> Do NOT write, edit, or delete any source code until the user has reviewed the plan and said "approved", "go ahead", "looks good", or equivalent.
> This rule is non-negotiable. If you start coding before receiving approval you are violating this workflow.

7. **Implement Changes:** Start coding only after the user has explicitly approved the implementation plan. Follow the existing project conventions and keep code changes tight to the task scope.

8. **Update Documentation:** After implementation, update the Markdown files to reflect the actual changes, testing results, and any deviations from the original plan.

**Important:** Do not directly modify existing code without first understanding and documenting its current behavior. Avoid unnecessary refactoring or changes outside the task scope.

# Mandatory Development and Git Workflow

## 1. Repository Structure

The original repository is configured as `upstream`.

My personal fork is configured as `origin`.

All development must follow this workflow:

1. Maintain my personal development instructions in `CLAUDE.md`.
2. Keep `CLAUDE.md` committed in my fork's `master` branch.
3. Create development branches from my fork's `master`.
4. Create a dedicated `tasks/<TASK-ID>-<task-name>/` directory for every new task.
5. Commit implementation code and task documentation in my internal development branch.
6. Create a separate clean PR branch based on `upstream/master` (or the actual upstream target branch).
7. Transfer only the required implementation changes into that clean PR branch.
8. Create an upstream PR only when implementation, milestones, and testing are complete.

## 2. Mandatory Task Directory

The `tasks/` directory has two levels:

```text
tasks/
├── instructions/                        ← template files (committed in master, never modified)
│   ├── task.md
│   ├── existing-implementation.md
│   ├── requirements.md
│   ├── implementation-plan.md
│   ├── impact-analysis.md
│   ├── milestone.md
│   └── test-cases.md
└── <TASK-ID>-<task-name>/               ← created on the dev branch when a task is assigned
    ├── task.md
    ├── existing-implementation.md
    ├── requirements.md
    ├── implementation-plan.md
    ├── impact-analysis.md
    ├── milestone.md
    └── test-cases.md
```

- `tasks/instructions/` holds the blank template files. These live in `master` and are never filled with implementation content.
- When a task is assigned, create the dev branch and copy the templates into `tasks/<TASK-ID>-<task-name>/`. Fill them in there.
- Task folders (`tasks/<TASK-ID>-*/`) must never appear in master or in upstream PRs.

These files must be maintained throughout development.

## 3. Strict Internal Branch Commit Rules

On my internal development branch:

- Always commit implementation changes.
- Always commit the complete task directory.
- Always update and commit `milestone.md` when progress changes.
- Include `CLAUDE.md` when it has been legitimately updated.
- Never exclude task documentation from internal development commits.
- Keep all progress available in my fork for future reference.

Do not automatically push incomplete work to the original upstream repository.

## 4. CLAUDE.md Protection

`CLAUDE.md` is a permanent, fork-specific instruction file.

Rules:

- Maintain and version-control `CLAUDE.md` in my fork's `master`.
- Development branches must inherit this file.
- Do not delete, overwrite, or reset my instructions when synchronizing changes from upstream.
- Do not replace my instructions with any upstream version of `CLAUDE.md`.
- If upstream changes conflict with this file, resolve the conflict while preserving my fork-specific instructions.
- Never include fork-specific changes to `CLAUDE.md` in an upstream PR.
- Do not add `CLAUDE.md` to `.gitignore` to solve PR exclusions.

## 5. Upstream Synchronization

When synchronizing my fork with upstream:

1. Fetch the latest changes from upstream.
2. Integrate upstream changes into my fork's `master`.
3. Preserve my committed `CLAUDE.md`.
4. Resolve any conflicts without discarding personal instructions.
5. Verify `CLAUDE.md` after synchronization.
6. Push the synchronized branch to my fork.

Never use destructive reset, force-push, or automatic conflict resolution that discards my `CLAUDE.md` without explicit approval.

## 6. Mandatory PR Exclusion Rules

The following files and directories are strictly prohibited from appearing as changes in upstream Pull Requests:

```text
CLAUDE.md
tasks/**
```

This restriction includes added, modified, renamed, and deleted files.

These files must remain committed in my internal development branch.

Do not delete them from the internal branch to prepare the PR.

Instead, create a separate clean PR branch from the actual upstream target branch and transfer only the approved implementation changes.

Never rely on `.gitignore` to remove already-tracked files from a PR.

## 7. PR Branch Preparation

Before preparing the Pull Request:

1. Confirm all implementation milestones are complete.
2. Confirm testing and regression checks have passed.
3. Update and commit `milestone.md` in the internal development branch.
4. Commit all remaining task documentation.
5. Fetch the latest upstream branch.
6. Create a clean PR branch from upstream.
7. Transfer only the required source-code, test-code, configuration, and other approved project changes.
8. Review the complete PR diff against upstream.
9. Verify `CLAUDE.md` and `tasks/**` do not appear in the PR diff.
10. Push the clean PR branch to my fork.
11. Create the PR targeting the original upstream repository.

Do not blindly cherry-pick internal commits containing task documentation into the PR branch.

## 8. Mandatory PR Validation

Before creating or updating a PR, execute:

```bash
git diff --name-status upstream/master...HEAD
```

Verify that the PR diff contains only approved project changes.

Reject PR preparation if any of the following appear in the diff:

- `CLAUDE.md`
- `tasks/` or any files inside it

Also verify the branch's commits and check for accidental sensitive information.

## 9. Milestone Completion Rule

Do not create a PR until:

- All required development is finished.
- All planned milestones are completed.
- Acceptance criteria are satisfied.
- Required testing is completed.
- The implementation has been reviewed.
- The internal development branch is committed.
- `milestone.md` reflects the verified final status.
- The clean PR branch has passed all exclusion checks.

## 10. Non-Negotiable Rules

**Internal development branch:** Implementation + task documentation must be committed.

**Fork master:** Preserve the permanent `CLAUDE.md` instructions.

**Upstream PR:** Implementation changes only. No fork-specific `CLAUDE.md` changes or task documentation changes.

These rules must be followed for every task without exception unless I explicitly authorize a different workflow.
